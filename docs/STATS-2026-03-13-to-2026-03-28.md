## 0. Metric Framework (Why Raw Latency Is Not Comparable)

Raw `totalMs` is **not a valid cross-period comparison metric**. A 2-minute recording will always take longer to process than a 5-second one. If usage shifts toward longer recordings (as it did this period: median 30s vs. shorter in baseline), raw latency looks worse even if the code got faster.

### Primary metric: RTF (Real-Time Factor)

```
RTF = processingMs / recordingDurationMs
```

Industry-standard for STT evaluation. RTF = 0.05 means processing takes 5% of the recording's duration — 20x faster than real-time. **Lower is always better. Scale-invariant.**

### Secondary metric: Fixed vs. variable cost decomposition

Using OLS linear regression `totalMs = fixed + slope × recordingDurationMs`:

- **Fixed overhead** = constant per-session cost (process spawn, API handshake, connection setup). Can't be eliminated without architectural change. Currently ~1479ms.
- **Variable rate** = additional processing per second of audio. Currently ~15ms/s. This is what parallelization reduces.

R² = 0.21 — duration explains only **21% of variance**. The dominant factor is fixed overhead, not audio length. This means optimizing fixed overhead has higher ROI than optimizing variable rate.

### Tertiary metric: ms/word

```
ms/word ≈ totalMs / (textLength / 5)
```

Output-normalized. Useful for comparing "how fast are we delivering usable text" independent of both recording length and verbosity.

### Going forward: track all three

| Metric | Current (Mar 13–28) | Interpretation |
|--------|--------------------|-|
| **Median RTF** | **0.055** | Processing takes 5.5% of recording duration |
| **Fixed overhead** | **~1479ms** | Per-session floor regardless of audio length |
| **Variable rate** | **~15ms/s of audio** | Scales well; not the bottleneck |
| **Median ms/word** | **27ms** | 27ms of processing per word of output |

## 11. Top Improvement Opportunities

Ranked by **impact on RTF and fixed overhead**, not raw latency.

### P0 — Parallelize ffmpeg conversion + Groq upload (Fixed overhead: −743ms)
- **Metric impact:** Fixed overhead 1479ms → ~736ms. Median RTF improves from 0.055 → ~0.030
- **Current state:** ffmpeg runs, finishes, then Groq upload begins. Sequential.
- **Data:** Conversion fixed cost ~743ms; Groq fixed cost ~466ms. They share no resources.
- **Implementation:** Start Groq upload of opus-encoded stream while ffmpeg is still writing; or buffer raw PCM and pipe directly to Groq after conversion completes in parallel with Deepgram streaming.
- **Note:** Already identified in Mar 3–12 analysis. Highest-ROI unimplemented improvement.

### P1 — Expand deterministic merge gating (Merge: −569ms on more sessions)
- **Metric impact:** Each additional session gated away from LLM saves 568ms of merge time
- **Current state:** 23% skip rate (12/52 eligible sessions). LLM merge still dominates at 72%.
- **Data:** `diff_below_threshold` + `punctuation_stripped_match` + `normalized_match` = 12 sessions; all paid ~1ms merge vs 569ms avg
- **Opportunity:** Lower gating thresholds for short transcripts (<200 chars), add similarity-score fast-path
- **Target:** Push skip rate from 23% → 40%+

### P2 — Tune Deepgram `endpointing` (Deepgram stop reason quality)
- **Metric impact:** 80% of sessions hit `finalize_timeout`; only 19% get clean `finalize_transcript`
- **Current:** `endpointing=300` (300ms silence threshold before marking speech final)
- **Opportunity:** Try `endpointing=150`. Faster speech-boundary detection = Deepgram closes cleanly instead of waiting for timeout → reduces deepgram wait time after recording stops
- **Risk:** More false positives on short pauses; evaluate empirically

### P3 — Fast-fail on Groq 503 (Error resilience)
- **Metric impact:** Saves 2 burned retry cycles (~30s each) during outages
- **Current state:** On 503, retry logic exhausts 3 attempts with 15s backoff against the same region
- **Data:** Mar 17 — bom region was down; all retries failed, wasting ~30s before Deepgram fallback
- **Fix:** On HTTP 503 with `x-groq-region` in response, immediately trigger Deepgram-only path; don't retry the same regional endpoint

### P4 — Short-recording fast path (<5s)
- **Metric impact:** <5s sessions have RTF 0.432 (worst in the distribution)
- **Root cause:** Fixed overhead (~1479ms) is 50–100% of total time for a 2–3s recording
- **Opportunity:** Skip Deepgram streaming entirely for <5s recordings (too short for streaming to be useful); use Deepgram batch REST + Groq batch in parallel
- **Expected RTF for <5s:** Could drop from 0.43 → ~0.15 by removing WS setup/teardown overhead
